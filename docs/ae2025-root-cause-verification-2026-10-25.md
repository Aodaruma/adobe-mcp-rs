# AE2025 MCP停止の原因切り分け・修正案（2026-10-25〜26）

後続調査: 10月26日の[仕様・設計監査](ae2025-architecture-audit-2026-10-26.md)で、時間猶予だけでは覆えない実行境界・状態確定・復旧経路の問題を隔離検証した。過去のbusyフラグもcommandTickActiveまで絞れた。本報告はその監査前の実機比較記録として保持する。

2026年10月25日23:47〜26日00:01 JSTに、このPCのAfter Effects 2025（25.6.6x4）で検証した。開始時にAEは起動していなかったため、新規の検証専用プロジェクトを使用した。制作AEPは開いていない。

**今回、新しく実機で確認できた不具合は「AEによる一時的な実行待ちから復帰した直後、内部監視が故障と誤判定してブリッジを再初期化する」ことである。** 修正候補で同じ条件の誤再初期化を防げた。一方、過去の全定期処理停止や、処理中フラグが約21分残った現象の根本条件までは解明できていない。

## 確定した仕組み

ブリッジの命令受信、heartbeat更新、内部監視（watchdog）は、今回のAEでは同じ `main` engineで動いていた。AEが同期処理を実行している間は、監視も含めて実行が遅れる。

旧版は監視が先に再開すると、命令受信やheartbeatの古い実行時刻を見て停止と判定する。他の予約が再開する順番を待たず、残っている予約を取り消してruntimeを作り直す。つまり、監視自身が待たされていた時間を、監視対象だけの故障と取り違える。

MCP経由の長い命令については既存コードに占有時間の補正があるが、今回の試験はMCP命令の外側で予約した同期処理であり、その補正に入らない。今回、監視側にも復帰直後の猶予が必要だと確認できた。

レンダー中、独立した1秒ごとの観測scriptも実行されなかった。終了直後は古い時刻のため一時的にhealthy=falseだったが、実際のcallback再開でhealthy=trueへ戻った。正常値を偽って書いたわけではない。外部復旧のjournalは開始前と同一で、今回の結果に外部復旧が介入した証跡はない。

## 作成した修正候補

`src/scripts/mcp-bridge-auto.jsx` のwatchdogに、自身の前回実行からの経過時間を記録する処理を追加した。監視も12秒超遅れていた場合は、復帰後の3秒間、watchdogによる故障判定を保留する。これにより、待機していた命令受信とheartbeatに実行機会を与える。

猶予中もheartbeatや実行回数を捏造しない。予約が本当に失われているケースでは、猶予後に復旧する。Node VMでは再開後9秒以内の観測で復旧と3種類の実行再開を確認した。監視自身まで完全に止まった場合を、この修正だけで直すものではない。

前回作成したlive renderQueueActive保護も候補に含む。ただし、今回の実レンダーでは処理中にwatchdogが動かなかったため、「レンダー中にwatchdogだけ動く」分岐の直接確認は引き続き隔離テストによる。

候補のSHA-256は `E684673AB2E6BB92EEC3D80F17C2133F74E27AD269DC077423250117C812C1B2`。検証時は空のAEへメモリ上で読み込み、終了時に除去した。Program Filesへの配置、バージョン更新、commit、公開releaseは行っていない。通常の次回起動には導入済みruntimeが使われる。

## 残る原因と、提案する順序

1. **まず今回の誤再初期化対策とレンダー保護を正式更新候補にする。** 実機で再現と改善が得られた範囲である。正式導入時は版番号・ソース・配置先の一致、通常起動と再起動後の稼働まで確認する。今回の猶予はwatchdog入口の対策なので、panel refreshなど別の自動復旧入口にも同じ「復帰待ち」の扱いが必要か検討する。
2. **処理中フラグの内訳を記録する。** 現在のcallbackActiveは、commandTickActive、heartbeatTickActive、isChecking、currentRequestIdをまとめた値である。currentRequestIdが空でも残ることは分かっているが、過去の記録だけではどのフラグが残ったか判別できない。各callbackの開始・終了・再予約・結果書込の段階、時刻、runtime世代、request IDを小さな循環ログに記録する案を推奨する。スクリプト本文や制作データの常時記録は不要。
3. **状態表示で「応答待ち」と「故障確定」を分ける。** 古いheartbeatだけから現在レンダーしていないとは判断できない。長い命令、レンダー、dialog待ち、予約消失、処理中状態不明を区別して表示し、実行開始済みの命令は再送しない。監視が進まない時間帯に、外部から確定できない状態を推測で埋めない。
4. **残る再現試験を狭く行う。** 次の焦点はfile dialogの表示／取消、スクリプトの実際の異常中断、結果書込〜次回予約の境界である。これは今回未解明のフラグ滞留・native modal拒否に対応する。経過時間だけでbusyを強制解除する案は、実行中の処理と競合するため採用しない。

今回の16秒試験は、過去の制作中停止をそのまま再現した試験ではない。誤再初期化が長期停止の全件を引き起こした、あるいは今回の候補で全再発が解消したとは結論しない。UXPなど別の実行方式への置換を決める前に、上記の段階記録で残る停止箇所を絞る方が、今回の証拠に沿っている。

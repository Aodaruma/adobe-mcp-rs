# AE2025 MCP接続停止の調査・修正報告

追記: 本文は追加実験前の経緯報告。その後、利用者の検証依頼を受けて10月25日夜〜26日未明に実機検証した結果は、[原因切り分け・修正案](ae2025-root-cause-verification-2026-10-25.md)に分けて記録している。

2026年10月25日作成。対象はこのPCのAfter Effects 2025（25.6.6x4）、調査・実機検証は主に10月22〜24日。10月25日は記録・コード・導入ファイルを読み取り確認して本報告をまとめた。AEの実行・状態照会・再起動・追加導入は行っていない。

今回、AE本体は開いていても、MCP用の定期処理が進まなくなり、外部から「接続先0件」と見える状態が発生した。その際に、停止を見抜けない、復旧処理に到達しない、過去の復旧成功を現在の状態として表示する、という複数のブリッジ側の不具合が重なっていた。これらの具体的な欠落は修正した。一方、AEが定期処理を止める全条件と、内部の処理中フラグが残る条件は確定していないため、恒久解消とは判断していない。

ブリッジは、AE内で「命令を受け取る処理」「heartbeatという生存記録を更新する処理」「それらを監視する処理」を定期実行する。起動時に記録を1回書けたことや予約番号を取得できたことだけでは、その後も動いているとは限らない。この区別が診断と復旧の中心になった。

| 確認した問題 | 対応 | 状態・限界 |
|---|---|---|
| 過去の修正を含むソースと、PCに導入された旧版0.5.3が一致していなかった | AE用JSXを0.5.4へ更新し、Startup・runtime・Shutdownの実ファイルをハッシュ照合して配置 | 導入済み。同版番号の別内容を保護して更新を見送るinstaller条件は確認したが、過去にそれが発生したログは未確認 |
| 命令受信とheartbeatが止まると、自力で復旧処理を呼べない | AE内の監視を整備し、監視まで止まるケースには常駐MCPアプリからの外部復旧経路を追加 | 導入済み。全3処理の取消・初回実行0回からの復旧を空プロジェクトで実機確認 |
| 命令受信側のheartbeat更新が、heartbeat専用処理の停止を隠していた。初回の書き込みも稼働に見えた | 3種類の実行回数をruntime世代別に記録し、実際の進行で稼働を判定 | 導入済み。手動更新や初回の書き込みだけで稼働確認済みとはしない |
| 長い命令の完了直後を停止と誤判定する経路や、実行開始後のエラーで命令を再送する経路があった | 実行中・完了時刻の扱いを修正し、古い世代の遅延callbackを無効化。開始後のmodalエラーを無条件に再送する処理を削除 | 導入済み。受付済み処理やtimeout後の未完了処理を保全し、復旧で制作命令を再実行しない |
| 同一AE起動中の候補記録が10件残り、復旧対象を1件に決められず外部復旧を見送っていた | 保存済み復旧履歴のprocess ID・開始時刻・instanceを照合し、一意に特定できる場合だけ対象を選ぶ | 10月24日導入済み。新しい記録を推測で選んだり、残存記録を削除したりはしない |
| 接続が再び止まっても、過去のrecovered表示が残った | 同じinstanceの現在のheartbeatと実行状況を確認して表示する | 10月24日導入済み。過去の成功履歴だけでは接続成功と表示しない |
| currentRequestIdが空でもcallbackActiveという処理中フラグが約21分残り、Restart Bridgeも外部復旧も拒否された | 安全確認を強制解除せず、ユーザーの保存完了と許可後にAE2025を再起動して復旧 | 対処済みだが根本条件は未確定。このケースを自動で修復したわけではない |
| 内部監視の復旧処理には、実際のレンダー中状態を確認する保護が不足していた | 内部のhealth確認と再初期化入口にlive renderQueueActiveの確認を追加 | **未導入の修正候補**。隔離テストで欠落を再現・修正確認したが、今回の実機停止との直接因果は未確定 |

導入は、10月23日にAE用JSXと外部復旧を含むMCPアプリ、10月24日01:03に対象選択・状態表示の追加修正版MCPアプリを配置した。10月25日の読み取り照合でも、導入中の4ファイルは記録したハッシュと一致した。レンダー保護候補は導入されていない。外部復旧はこのPCのAE2025向けに明示的に有効化し、製品の既定値は無効のままとしている。

「復旧要求を送れた」「AEが要求を受け取った」「定期処理が再び進んだ」は別々に確認した。外部復旧は対象processとruntimeを照合し、期限を設け、進行を確認して初めて成功とする。処理中・要求の状態不明・既知のレンダー中・dialog表示中などは見送り、失敗時の再試行回数も記録する。ただし古いheartbeatにレンダー開始が反映されていなければ、外部launcherが最初の試行をする余地は残る。実行入口のlive render確認と期限保護があっても、外部から現在の安全な実行可否を完全には判定できない。

検証は段階ごとに行った。以下は異なる修正段階の件数であり、合算して最終版の試験件数とはしない。

| 段階 | 確認結果 |
|---|---|
| 10月23日の外部復旧候補 | Rust全workspace 134件成功、Node VM 15件成功、Windows ES3 18件成功 |
| 10月24日の対象選択・表示修正 | daemon-core 31件成功。修正前には追加回帰テスト2件が想定どおり失敗し、修正後に成功。変更対象Clippy・release buildも成功 |
| 10月24日の未導入レンダー保護候補 | Node VM 17件、Windows ES3 18件成功。追加2ケースは修正前に失敗、修正後に成功 |
| AE2025実機 | 通常起動、全3処理の停止、初回実行0回からの復旧、dialog表示中の見送り、長い命令のtimeout後の1回完了、制作AEPを開き直した後のMCP応答を確認 |

全workspaceを対象とした厳格Clippyには、今回変更していない箇所の既存警告が残った。変更対象のチェックは成功した。複数AE、全dialog操作、終了直前の競合、長時間連続制作をすべて実機で網羅したものではない。

再発を繰り返した理由は、最初の修正で塞いだ経路とは別の停止・復旧阻害条件が後から観測されたためである。内部監視を追加しても、その監視自体がAEの同じ定期実行機構に依存していた。外部復旧を追加した後には、残存記録の曖昧さと処理中フラグの滞留が復旧を阻害した。さらに、レンダーや長いscript実行による応答待ちも、見かけ上同じ「接続0件」「timeout」になり得た。初期の成功試験は確認した条件での復旧を示すもので、自然発生条件すべての解消を示していなかった。

10月24日のレンダー中の停止は、報告元が02:48に実MCPで回復とrender=falseを確認した。修正候補の導入や元担当による手動Restart・AE再起動は行われていない。runtimeの更新と内部復旧履歴はあるが、直接の回復契機は未確定である。その後の約1分の数値評価scriptは10秒のtool timeoutになったものの、同じrequestが最終completed・errors=[]となった。こちらは既知の長時間処理として区別し、未説明停止の再発には数えない。

未確定なのは、AEが定期予約を実行しなくなる個別条件、処理中フラグが残る条件、見えるdialogがなくてもnative実行をmodal扱いで拒否する条件である。ファイル選択後の拒否は実機で再現し、閉じて約25秒待っても発生したため、待ち時間の追加だけを解決策とはしていない。起動時にはS_Distortに関するAEの異常終了通知も観測したが、MCP停止との因果を示す証拠はなく、原因と断定していない。

残作業は、未導入のレンダー保護候補を制作停止・保存済みの時間に配置し、実レンダーを挟んで検証すること、処理中フラグ滞留と全定期処理停止の発生条件を絞ること、修正を通常の配布・更新経路へまとめることである。現時点の変更は `fix/ae-docked-bridge-recovery` の作業用checkoutに保存されており、今回の変更のcommit・mainへの反映・公開releaseは未実施。本報告の依頼を追加導入や再起動の依頼とは扱っていない。
